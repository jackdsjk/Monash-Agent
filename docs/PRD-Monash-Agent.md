# Cove 精简 PRD

> 版本：v0.3
>
> 日期：2026-10-29
>
> 状态：可修改的决策草案；MVP P0 范围已按 [MVP 范围决策](mvp-scope-2026-10-29.md) 锁定初版

## 1. 摘要

Cove 是一款面向 Monash 学生的本地优先应用。第一版以本地 Web App 验证，桌面壳后置。它在后台运行受约束的 Agent 工作流，巡检 Moodle、学校邮箱和 Ed，把分散的大量内容压缩成带原文依据的“自上次查看以来”简报。

产品不替学生完成作业，也不只是增加日历提醒。它首先替用户完成跨平台巡检、阅读、筛选、合并和初步判断，让用户只在真正重要或不确定时返回原文。

## 2. 负责人

这是独立产品项目。项目所有者负责问题定义、方案取舍和最终交付；第三方开源组件及 AI 辅助产出单独说明，不写成个人独立完成。

## 3. 背景

学生目前可以分别打开 Moodle、学校邮箱和 Ed 查看信息，但必须频繁切换平台并逐条判断：内容是否与自己有关、是否来自教学人员、是否改变作业要求、是否需要行动，以及是否已在其他平台看过。

2026-10-28 的第一轮只读回放显示：最近 7 天共有 39 封邮件和 68 个 Ed 主题。Ed 主题中 7 个由教学人员发起、61 个由学生发起；39 封邮件中 24 封尚未被现有规则归属到具体课程。样本中还出现了同一提醒分别从 Ed 和邮件发送、但标题不完全一致的情况。这些数据只证明信息量、来源混杂和语义重复确实存在，尚未证明产品已经节省时间或避免遗漏。

项目已经验证 Moodle、Ed、OnTrack 和 Gmail 的真实读取能力。当前缺口不是增加连接器，而是建立可靠的信息分诊标准，并把已有能力组织成普通学生能够直接使用的产品。

## 4. 目标

### 产品目标

让学生无需逐条浏览多个学校平台，也能快速知道：最近发生了什么、哪些值得关注、为什么值得关注，以及需要核对哪段原文。

### 第一阶段成功标准

以下均为目标，不是当前结果：

1. 建立不少于 50 条匿名化真实样本的人工 Gold Set，覆盖邮件、Ed 和 Moodle，并明确重要性、信息类型、权威性、行动性和证据。
2. 在 Gold Set 上分别报告重要信息召回率、低价值内容压缩率、摘要忠实度、课程归属和语义重复识别结果。
3. 用户可以在匿名演示模式中走通“同步新内容—查看简报—核对证据—打开原文—纠正判断”的完整流程。

真实用户节省时间、留存、遗漏规避次数和付费意愿，等具备用户验证条件后再加入，不提前声称。

## 5. 目标市场与用户

### 第一目标用户

同时使用 Moodle、学校邮箱和 Ed，需要定期确认课程动态，但不希望逐条阅读所有通知与讨论的 Monash 学生。

他们的核心任务不是“再建一个日历”，而是以尽可能低的精力确认自己没有错过真正重要的信息。

主要约束：

- 邮件、课程记录和讨论内容属于敏感数据；
- SSO、MFA 和会话过期会影响首次使用；
- 不同来源的时间字段、作者身份和内容结构不同；
- 学生提问可能只有在教师回复后才变得重要；
- AI 不能把学生猜测写成学校正式要求；
- 当前尚无外部用户研究，第一阶段以历史数据回放和自用测试验证。

### 后续用户

希望通过 MCP、CLI 或 API 将 Monash 数据接入自有 Agent 的技术用户。该入口复用相同的数据与分诊能力，但不主导普通用户体验。

## 6. 价值主张

- **Who：**需要在多个学校平台持续确认课程动态的学生。
- **Why：**他们不敢只看部分信息，怕漏掉重要要求；但逐条阅读全部内容又消耗大量注意力。
- **What before：**每天分别打开 Moodle、邮箱和 Ed，浏览大量公告、学生讨论和重复通知，再自行判断哪些需要处理。
- **How：**产品自动巡检新内容，按课程和权威性整理，提炼教师结论，识别重要变化与语义重复，并给出带原文证据的简报。
- **What after：**用户先阅读少量高价值结论，只在必要时打开原文，而不再把“逐个平台排查”作为每天的固定劳动。
- **Alternatives：**直接查看 Moodle、邮箱和 Ed，或手动复制到日历、Todo、Notion。Cove 的差异不是存放更多信息，而是替用户完成阅读前的分诊工作。

**价值主张：**不必把每条消息都看完，也能知道真正值得关注的事情，并能随时回到原文核对。

## 7. 解决方案

### 7.1 核心体验

主入口不是空白聊天框或月历，而是 **Today / Since Last Check**：

```text
连接数据源
→ 后台同步新内容
→ Agent 识别课程、作者权威性、信息类型和语义重复
→ 生成“必须处理 / 重要更新 / 教师答复 / 新资料 / 已折叠”简报
→ 用户查看关键原句与来源
→ 必要时打开原文，或纠正系统判断
```

聊天可以作为后续辅助入口，例如追问“这周 FIT1047 作业要求有什么变化”，但不作为第一版主界面。

### 7.2 第一版候选能力

1. **低门槛连接与同步：**用界面展示数据源状态、同步时间和失败原因，不要求用户使用 CLI。
2. **跨源信息流：**以邮件和 Ed 验证高频内容分诊，以 Moodle 提供课程与 assessment 的结构化事实。
3. **信息分诊：**区分必须处理、重要更新、教师答复、学习材料、一般信息和不确定内容。
4. **去重：**第一版处理同一来源的精确重复；跨平台语义合并在 P1 处理。
5. **证据优先：**关键结论展示原文关键句、作者身份、时间和原始链接；不确定时明确提示核对。
6. **用户反馈：**允许用户标记重要、不重要和分类/重要性错误；摘要反馈在摘要能力进入版本后再加。

P0 初版已锁定为五个能力域：本地 Web 入口与首次连接、三源只读同步与同步状态、Since Last Check 简报、证据与原文跳转、用户纠错与本地数据控制。完整取舍、评分和验收标准见 [MVP 范围与优先级决策](mvp-scope-2026-10-29.md)。

### 7.3 AI 应用边界

| 类型 | 职责 |
|---|---|
| 确定性程序 | 登录与同步、稳定 ID、来源链接、结构化日期、状态保存、精确重复和权限边界 |
| AI 辅助（P0 启用） | 信息类型、重要性建议和行动建议；输出必须带原文证据 |
| AI 辅助（P1 再启用） | 课程归属、内容摘要、教师结论提炼和语义重复候选 |
| 用户决定 | 处理来源冲突、确认高风险结论、纠正分类与重要性、决定后续行动 |

所有高影响结论必须有来源。AI 不得自动提交作业、回复教师，也不得把没有证据的推断写成事实。

### 7.4 假设与开放问题

- 107 条/7 天的信息量是否足以让目标用户持续使用，仍需回放和自用测试证明。
- “重要”是否能形成跨课程通用标准，还是需要按用户偏好学习。
- Ed 学生主题应按课程、教师回复、热度还是用户当前任务排序，尚待样本分析。
- Moodle assessment 的时间字段表示截止时间，不能与邮件、Ed 的发布时间直接比较；统一时间模型仍需设计。
- 第一版技术形态暂定为本地 Web App；桌面壳在 P1 评估，不阻塞本地验证。

## 8. 发布边界

### 第一版

- 一个可在本地启动的 Web 入口（桌面壳 P1）；
- Gmail、Ed 与 Moodle 的最小纵向切片，以及同步状态和失败提示；
- Today / Since Last Check 简报；
- 信息详情、关键原句和原文跳转；
- 用户纠错与本地数据查看/清除；
- 已有匿名演示原型和不少于 50 条样本的评测集。

### 后续版本候选

- OnTrack 和更多来源；
- 个性化重要性排序；
- 课程规则与后果解释；
- 日历和提醒；
- 辅助问答；
- MCP/CLI 技术用户入口；
- 经批准后的真实用户测试。

### 明确不做

- 以聊天框为主体的通用 Agent；
- 单纯的日历或截止日期提醒器；
- 自动完成、提交作业或代表用户发消息；
- 多学校、住房、签证和校园社区；
- 当前阶段的增长、付费和内容运营；
- 为匹配 JD 增加无关的 Dify、Coze 或多 Agent 功能。
