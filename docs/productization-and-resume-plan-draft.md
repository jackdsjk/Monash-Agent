## 1. 项目目标

### 1.1 第一目标：形成真正可用的 C 端产品

把散落的 Monash CLI、MCP、邮件和课程数据能力，组织成一个普通学生可以理解、安装和使用的完整工作流，而不是继续增加彼此独立的工具。

### 1.2 第二目标：形成可核验的求职项目

项目过程需要真实覆盖：

1. 发现问题；
2. 定义目标用户与需求；
3. 竞品和替代方案调研；
4. 需求优先级与功能取舍；
5. MVP 方案和原型；
6. 产品开发与上线；
7. 质量评测与 Bad Case；
8. 用户反馈、数据复盘和迭代；
9. Demo、One-pager 和复盘材料。

同一组真实事实可以根据 JD 分别支持产品经理、AI 产品开发和产品运营简历，但不拆成三段虚构经历。

### 1.3 第三目标：保留商业化可能

在核心产品稳定后，再验证安装服务、基础版、完整版本或后续增值服务的付费可能。商业化不阻塞当前 MVP，也不作为现阶段成功的唯一标准。

## 2. 当前事实、判断与假设

### 2.1 已确认事实

- Monash 相关开源生态已经存在 Moodle、Ed、OnTrack、邮件及 MCP/Agent 接入工具；
- 现有能力以 CLI、插件和单点工具为主，需要分别发现、安装、配置和调用；
- 项目已完成 Moodle、Ed、OnTrack 的真实连接验证；
- 项目已完成 Gmail 数据接入、批量读取、分页、幂等、异常分类和中文标题解码等验证；
- 项目已有关于许可证、隐私、本地存储、可信来源和商业限制的调研；
- 根项目当前尚未形成一个普通用户可以完整操作的独立应用和闭环界面。

### 2.2 当前产品判断

现有生态的主要问题可能不在“缺少更多插件”，而在以下三层断裂：

1. **发现断裂**：非技术用户不知道 GitHub、CLI 或 MCP 工具的存在；
2. **安装断裂**：用户需要分别安装运行环境、工具、凭据和插件；
3. **工作流断裂**：不同工具只能读取各自数据，没有统一事项、优先级、来源、确认、提醒和完成闭环。

这意味着 Cove 的产品价值不应只是“再写一个连接器”，而应是：

> 把已有连接能力编排成一个低门槛、可追溯、可行动的学生工作流。

### 2.3 待验证假设

- 非 CS 用户比 CS 用户更容易受到安装、配置和概念理解门槛影响；
- 学生的主要痛点可能是信息分散、重要性判断困难或看见后忘记行动；
- 用户愿意授权产品读取 Moodle 或学校邮箱；
- 原始来源、最小权限和本地优先能够提升用户信任；
- 用户愿意安装桌面应用，或者愿意通过更轻量的入口使用；
- 相比纯聚合，风险判断、去重和行动提醒更可能形成持续使用价值；
- 一体化工作流能够产生付费或推荐意愿。

这些假设在得到证据前，不写成简历中的用户结论。

## 3. 产品定位

### 3.1 暂定名称

**Cove｜Monash 学业风险与行动助手**

名称可以在用户研究、品牌设计或商业测试后修改。“Agent”是技术和品牌表达，不代表产品必须以聊天机器人作为主界面。

### 3.2 一句话定位

面向 Monash 学生，将 Moodle 和学校邮件中的分散信息转化为可确认、可追溯、有优先级的行动事项，并通过统一工作流降低重要任务遗漏。

### 3.3 初步目标用户

第一阶段聚焦 Monash Malaysia 学生，优先考虑：

- 刚入学、尚不熟悉学校系统和课程规则的学生；
- 同时使用 Moodle、学校邮箱、Ed 或 OnTrack 的学生；
- 希望减少手动检查平台，但不熟悉 GitHub、CLI 或 MCP 的非技术用户；
- 曾经遗漏公告、日期变更、课程要求或提交任务的学生。

最终目标用户以实际证据为准，不预设“所有学生都需要”。

### 3.4 核心待验证任务（JTBD）

> 当课程信息分散在多个平台时，我希望快速知道哪些事情需要我行动、什么时候完成、判断依据是什么，以便减少遗漏和反复检查。

### 3.5 产品差异化

不是：

- 另一个 Moodle 客户端；
- 一组需要单独安装的 MCP 插件；
- 通用 AI 聊天助手；
- 自动写作业或自动提交工具；
- 只展示截止日期的日历。

而是：

- 将多个来源组织成一条完整行动链路；
- 默认面向不懂 GitHub 和命令行的普通学生；
- 每个关键结论保留原始来源和证据；
- 用户可以确认、纠错、忽略和完成；
- 对重复通知和低价值信息进行控制；
- 在必要时使用 AI 完成提取、分类和辅助判断。

## 4. 产品结构：一个核心，两种入口

### 4.1 普通用户入口（主产品）

提供低门槛的一体化应用，负责：

- 引导登录与授权；
- 自动发现可用数据源；
- 展示同步状态和失败原因；
- 生成统一行动事项；
- 展示来源、风险和提醒；
- 接受用户确认与纠错；
- 保存完成状态和反馈。

第一阶段可以是桌面应用，但 Windows、macOS 或 Web 的最终优先级仍需结合目标用户设备和实现成本确认。

### 4.2 技术用户入口（扩展能力）

保留 MCP、CLI 或 API 适配层，使技术用户可以把同一套数据和行动能力接入 Codex、Claude 或其他 Agent。

该入口不是第一阶段面向普通用户的默认体验，而是：

- 复用现有开源生态；
- 保持连接器可替换；
- 展示 AI 产品开发能力；
- 支持未来扩展。

### 4.3 产品真正负责的层

Cove 不需要重写所有底层工具。核心产品层负责：

```text
连接器与数据源
→ 统一数据模型
→ 行动项识别与去重
→ 风险和证据展示
→ 用户确认与纠错
→ 提醒与完成状态
→ 评测、反馈和迭代
```

## 5. MVP 范围

### 5.1 MVP 核心承诺

> 让用户在一个地方看到近期需要行动的高风险学业事项，并知道系统为什么这样判断。

“不再遗漏任何事项”属于长期愿景，不作为第一版无法保证的绝对承诺。

### 5.2 MVP 核心流程

```text
连接 Moodle / 学校邮箱
→ 同步课程信息和近期消息
→ 识别需要行动的事项
→ 提取课程、日期、类型和来源
→ 合并疑似重复事项
→ 展示风险等级和原始证据
→ 用户确认、修改或忽略
→ 创建提醒
→ 用户标记完成
```

### 5.3 MVP 建议页面

1. **开始与授权**
   - 解释产品用途；
   - 说明读取范围和隐私边界；
   - 引导连接数据源；
   - 展示同步进度和错误。

2. **今日风险 / 行动收件箱**
   - 展示近期事项；
   - 按时间和风险排序；
   - 标记待确认、已确认、已忽略和已完成。

3. **事项详情**
   - 展示课程、日期、事项类型和风险；
   - 展示原始邮件或公告来源；
   - 允许用户确认、修改和反馈错误。

4. **提醒与设置**
   - 设置提醒时间；
   - 管理数据源；
   - 查看本地存储和删除数据选项。

### 5.4 第一版明确不做

- 万能 AI 对话；
- 自动完成或提交作业；
- 住房、签证、饮食和社交服务；
- 全量学校政策知识库；
- 多学校同时支持；
- 社区和内容平台；
- 复杂多 Agent 自主执行；
- 以获取大量用户为前提的增长系统。

## 6. 开发与验证阶段

以下是阶段边界，不是不可修改的固定日期排期。

### 阶段 A：产品定义与证据整理

目标：把已有技术能力翻译为清晰的用户问题和产品范围。

产物：

- 产品 One-pager；
- 当前替代方案和竞品矩阵；
- 用户问题与假设清单；
- 用户旅程草图；
- 需求池和优先级依据；
- MVP PRD；
- 关键流程原型；
- 指标和埋点定义。

完成标准：能够在两分钟内说明“为谁解决什么问题、为什么先做这些功能、如何判断有效”。

### 阶段 B：可操作 MVP

目标：从真实数据源走通完整核心流程，而不是继续增加独立连接器。

产物：

- 可安装或可启动的产品入口；
- Moodle 与学校邮箱接入；
- 统一事项模型；
- 今日风险列表和事项详情；
- 用户确认、纠错、忽略和完成状态；
- 基础提醒；
- 可演示的匿名化样本模式。

完成标准：首次使用者能够在不执行命令行操作的情况下完成核心任务；技术用户仍可通过适配层使用已有能力。

### 阶段 C：AI 质量与可靠性

目标：证明 AI 能力可评测、可纠错，而不是只展示一次成功结果。

产物：

- 匿名化评测集；
- 人工标准答案；
- 行动项、课程、日期、风险和去重评测；
- Bad Case 分类；
- 模型或规则版本记录；
- 错误提示、降级和人工确认机制。

完成标准：能够解释主要错误类型、当前质量边界和每轮迭代解决了什么问题。

### 阶段 D：可选真实用户验证

目标：在条件允许时验证需求、可用性和持续使用价值。

可选方式：

- 在小红书或 Monash 微信群发布匿名问卷；
- 邀请同学进行产品原型测试；
- 进行 8–12 名目标用户访谈；
- 选择 3–5 人进行短期日记研究；
- 招募小规模内测用户；
- 测试付费、帮装或推荐意愿。

该阶段目前不是阶段 A–C 的阻塞条件。若暂时无法接触真实用户，可先使用：

- 自己的历史数据回测；
- 匿名化样本测试；
- 启发式可用性检查；
- 竞品评论和公开用户反馈；
- 演示测试和任务完成测试。

但在没有真实用户时，不得在简历中声称已验证用户需求、留存、增长或付费。

### 阶段 E：运营与商业验证

目标：在产品核心稳定后，验证传播、激活和付费路径。

可选产物：

- 小红书内容和落地页；
- 内测招募漏斗；
- 安装与授权教程；
- 常见问题和客服 SOP；
- 推荐或邀请机制；
- 基础版、完整版本或帮装服务价格测试。

当前不以“做大知名度”为第一优先级。分发服务于产品验证和简历证据，不反过来挤占核心产品开发。

## 7. 评测与指标

### 7.1 AI / 规则质量指标

- 行动项识别 Precision / Recall；
- 截止日期提取准确率；
- 课程识别准确率；
- 重复事项合并准确率；
- 风险分类准确率；
- 无来源结论比例；
- 用户纠错率；
- 各类 Bad Case 数量及关闭情况。

### 7.2 产品体验指标

- 首次连接成功率；
- 首次同步成功率；
- 首次价值时间；
- 核心任务完成率；
- 事项确认率；
- 同步或授权失败原因分布；
- 提醒打开率；
- 已确认事项完成率。

### 7.3 用户与运营指标（获得真实用户后）

```text
看到招募内容
→ 进入产品介绍
→ 完成安装
→ 完成授权
→ 首次同步成功
→ 确认第一个事项
→ 一周内再次使用
→ 主动推荐或付费
```

可关注：

- 招募到安装转化率；
- 安装到激活转化率；
- 次周留存；
- 反馈闭环率；
- 推荐人数；
- 付费或帮装转化率。

### 7.4 价值指标

暂定核心价值指标：

> 每周经用户确认，并在截止时间前完成的高风险事项数。

“避免遗漏次数”存在反事实测量困难，需要结合历史回测、用户确认和提醒前后行为谨慎解释。

## 8. 用户研究的可选分级

用户研究暂不作为当前开发阻塞项，但应保留入口。

### Level 0：现在即可进行

- 复盘自己的真实使用流程；
- 整理历史遗漏、重复通知和规则判断案例；
- 分析现有 GitHub 工具的目标用户和安装流程；
- 收集公开评论、Issue 和使用反馈；
- 用历史数据进行产品回测。

### Level 1：轻量验证

- 小红书投票或问卷；
- 微信群匿名问卷；
- 原型演示后的任务测试；
- 收集设备、平台、通知习惯和授权顾虑。

### Level 2：深度验证

- 半结构化用户访谈；
- 屏幕共享观察用户现有流程；
- 一周日记研究；
- 小规模真实内测；
- 价格和推荐意愿测试。

是否进入 Level 1/2，由后续用户资源、产品成熟度和求职时间共同决定。

## 9. 面向三类简历的证据建设

### 9.1 通用产品经理方向

需要形成的真实证据：

- 用户问题和使用场景；
- 竞品与替代方案分析；
- 需求池与优先级判断；
- MVP 取舍；
- PRD 和原型；
- 可用性测试；
- 数据复盘和版本迭代；
- 隐私、可信度和商业化权衡。

核心叙事：

> 从多平台信息分散和行动判断困难出发，完成需求定义、产品取舍、MVP 设计和验证闭环。

### 9.2 AI 产品开发方向

需要形成的真实证据：

- 多数据源接入和统一数据模型；
- AI 提取、分类、去重和风险判断；
- 评测集与人工标准答案；
- Precision / Recall 等质量指标；
- Bad Case 分类和版本迭代；
- 人工确认、证据追踪和失败降级；
- Agent/MCP 与普通用户产品之间的适配层。

核心叙事：

> 将大模型能力嵌入真实用户流程，用评测、来源追踪和人工反馈控制错误，而不是只调用一次模型 API。

### 9.3 产品运营方向

需要形成的真实证据：

- 用户招募渠道；
- 安装、授权和激活漏斗；
- 用户反馈分类；
- 提醒策略和触达效果；
- FAQ、教程和 onboarding；
- 留存、推荐和付费测试；
- 根据数据调整运营方案。

核心叙事：

> 围绕非技术学生的安装和激活门槛，设计用户教育、反馈闭环和留存运营，并通过漏斗定位流失环节。

## 10. 简历表达规则

统一使用“背景—需求—行动—结果”结构。

### 10.1 当前已经可以写的内容

- 完成 Monash 学习工具和开源生态调研；
- 验证 Moodle、Ed、OnTrack 与 Gmail 的数据连接；
- 设计可信来源、隐私、本地优先和提醒方案；
- 实现 Gmail 数据批量获取、分页、幂等和异常处理；
- 分析许可证和商业使用边界。

### 10.2 完成后才能写的内容

- 完成可操作的独立应用；
- 完成评测集和质量指标；
- 完成用户测试和产品迭代；
- 获得真实内测用户；
- 验证留存、推荐或付费；
- 帮助用户避免遗漏重要事项。

### 10.3 禁止写法

- 把计划指标写成完成结果；
- 把第三方项目功能写成本人独立开发；
- 把个人项目写成不存在的公司实习；
- 编造用户数量、准确率、转化率或收入；
- 只写“参与项目”“负责优化”“提升体验”等无法验证的空话。

## 11. 最终项目交付包

项目达到可投递状态时，至少应有：

1. **One-pager**：用户、问题、定位、方案和指标；
2. **MVP PRD**：范围、流程、需求、异常和验收标准；
3. **竞品与生态分析**：现有工具、重叠、空白和取舍；
4. **可操作产品**：真实模式与匿名演示模式；
5. **两分钟 Demo**：从连接数据到确认行动事项；
6. **AI 评测报告**：数据集、指标、Bad Case 和迭代；
7. **用户或可用性验证报告**：若有真实用户则如实记录；
8. **指标复盘**：产品行为、质量和运营数据；
9. **Postmortem**：有效内容、失败内容、权衡和下一步；
10. **三套简历表述**：产品、AI 产品开发、产品运营。
