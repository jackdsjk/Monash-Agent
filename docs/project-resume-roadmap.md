# Cove 项目与简历证据路线图

> 日期：2026-10-28
>
> 原则：每一步必须产生可检查的产品成果和可核验的简历证据；计划目标不能提前写成结果。

## 总体定位

该项目在三段项目组合中主要承担：

1. **通用产品能力：**问题定义、竞品分析、需求取舍、MVP、交互和迭代；
2. **AI 产品能力：**AI 边界、人工确认、来源约束、评测和 Bad Case；
3. **AI 开发能力：**多源接入、结构化处理、状态、异常与可测试性，作为产品落地支撑。

运营、增长和商业化暂不进入当前路线。

## 第一步：产品定义

### 本步结论

- 产品不是另一组 Monash 插件，也不是提醒器，而是把现有能力编排成普通学生能够使用的信息分诊工作流。
- 第一目标用户暂定为需要持续检查 Moodle、学校邮箱和 Ed，但不希望逐条阅读全部内容的学生。
- 产品核心是“跨源巡检 + 信息分诊 + 语义合并 + 原始证据 + 用户纠错”。
- AI 只处理非结构化摘要、课程归属、语义去重和辅助分类；确定性事实、来源和高风险操作不交给模型独立决定。
- 技术用户的 MCP/CLI 接口保留为后续入口，不主导第一版体验。

### 已产生的证据

- 当前精简 PRD；
- 现有 GitHub 生态与许可证调查；
- Moodle、Ed、OnTrack、Gmail 的接入验证记录；
- 对“发现、安装、工作流”三层断裂的产品判断；
- 来源优先、冲突展示和永不自动提交的信任原则。

### 完成门槛

能够在 90 秒内回答：目标用户是谁、现有方案哪里断裂、第一版提供什么价值、AI 为什么只放在这些环节、哪些功能明确不做。

## 第二步：价值回放

从现有 Gmail、Ed 和 Moodle 数据中抽取不少于 50 条匿名样本，按统一规范完成两轮人工标注。回答：

- 哪些内容真正值得用户看到；
- 哪些内容可以安全折叠；
- 哪些结论只有结合教师身份、正文或跨源信息才能得到；
- “重要”是否能形成稳定、可解释的规则；
- 产品能否在高召回重要信息的同时减少阅读量。

输出：标注规范、Gold Set、价值回放报告和继续/停止判断。

当前已建立 55 条 Gmail 25、Ed 25、Moodle 5 的匿名改写样本，并完成两轮相互独立的
agent-assisted 标注与裁决记录。该资产用于流程和评测 harness 的开发；由于不是项目所有者
签核的真实脱敏样本，暂不能作为最终真人 Gold Set 或简历证据。

当前执行策略是先实现一个无模型、无网络、无新增依赖的最小离线回放器，快速验证
`importance`、`action_required`、`content_type`、`open_original` 和证据支持。完整的
多模型矩阵、复杂语义去重、CI 门禁和真实样本替换列入后续方案，不阻塞 MVP。

## 第三步：MVP 取舍

本步不直接开始写界面，而是先对候选功能评分。至少比较：

- Moodle、Gmail 与 Ed 的最小数据切片；
- 授权和同步；
- Today / Since Last Check 简报；
- 信息类型与重要性判断；
- 教师答复提炼；
- 精确与语义去重；
- 来源展示；
- 用户纠错；
- OnTrack、规则库、日历提醒、AI 对话和 MCP 入口。

输出必须明确：

- P0 功能及其对应的用户价值；
- 被砍掉或延后的功能及原因；
- 第一版唯一核心流程；
- 每个 P0 功能的完成标准；
- 技术风险和产品假设分开记录。

当前已产出 [MVP 范围与优先级决策](mvp-scope-2026-10-29.md)，并同步到 PRD v0.3；P0 初版待项目所有者确认。匿名 Demo 属于交互验证，不替代本步的取舍结论。

完成后，更新 PRD 的第一版范围。

## 第四步：AI 评测基线

围绕真实产品任务建立不少于 50 条匿名化样本，至少覆盖：

- 重要性与是否需要展示；
- 课程识别；
- 内容类型与作者权威性；
- 行动要求与时间线索；
- 语义重复；
- 摘要忠实度；
- 来源是否支持结论；
- 高风险误判和漏判。

输出一份基线报告，分别说明规则、模型和人工确认处理了什么。后续每次改模型、提示词或规则，都必须对相同样本回归。

## 第五步：可操作产品与 Demo

进入该步骤时安装：

- `frontend-design`：确定产品界面和交互方向；
- `web-design-guidelines`：审查界面、可访问性和状态反馈；
- `playwright-best-practices`：覆盖核心流程和失败场景。

本步交付：

- 不使用命令行即可完成核心任务的 MVP；
- 不含私人数据的匿名演示模式；
- 两分钟内可展示价值的 Demo；
- 登录、同步、分诊、证据、纠错和错误状态测试；
- 一次基于测试或回测结果的真实迭代。

## 第六步：简历和面试包

### 产品经理版本重点

- 为什么需求存在；
- 为什么选择该目标用户；
- 如何分析竞品和替代方案；
- 为什么选择这些 P0、砍掉哪些功能；
- 如何通过测试或数据改变第二版。

### AI 产品版本重点

- 为什么这些环节使用 AI；
- 如何处理概率性输出；
- 如何建立 Gold Set、指标与 Bad Case；
- 如何通过来源、人工确认和降级控制风险。

### AI 开发版本重点

- 多源适配和统一数据模型；
- 批量、分页、幂等、认证和异常处理；
- 结构化输出、规则与模型协作；
- 自动化测试和可替换边界。

### 最终求职交付

1. 一页项目说明；
2. 两分钟 Demo；
3. 项目复盘；
4. 产品经理版简历表述；
5. AI 产品版简历表述；
6. AI 开发版补充表述；
7. 可回答的面试问题与真实数据口径。

## 当前简历边界

目前可以证明的是生态调研、接入验证、产品判断、可信度设计和 Gmail 适配开发。当前还不能声称已经完成独立应用、获得用户、提高留存、避免遗漏或取得付费。

项目材料中的检索数量、技术结果和代码贡献，在进入正式简历前还需要由项目所有者确认自己能够解释，并区分本人实现、AI 辅助和第三方依赖。

## Career Ops 当前判断

**Verdict：VALIDATE THEN BUILD。** 当前版本已经从“包装 CLI”和“提醒器”转向“Agent 驱动的信息分诊产品”。真实数据初步证明信息量与混杂度存在，但尚未证明能够可靠压缩阅读成本。先完成价值回放和 Gold Set，再锁定 MVP。
